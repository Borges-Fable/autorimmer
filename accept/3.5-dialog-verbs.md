# Acceptance — spec 3.5, dialog + interaction verbs (git-bug `20e5cda`)

…and its hard dependency, the quest observer (git-bug `548ef48`).

The worker that wrote 3.5 may never launch RimWorld, so the acceptance ships in
executable form. `accept/3.5-dialog-verbs.py` runs every step and prints
`PASS`/`FAIL` per numbered check; `accept/3.5-dialog-verbs.ps1` is its BORGES
twin. **This file is the post-mortem of the checks, not a second copy of them** —
read the driver for the sequence and read this for why the phase-3 checks say
what they say.

```
python3 accept/3.5-dialog-verbs.py               # everything, 189 expectations
python3 accept/3.5-dialog-verbs.py --phase 3     # one phase (phase 0 always runs first)
python3 accept/3.5-dialog-verbs.py --dry-run     # print the plan, send nothing
python3 accept/3.5-dialog-verbs.py --root <path> # a protocol root elsewhere
python3 accept/3.5-dialog-verbs.py --echo        # print every result envelope
pwsh accept\3.5-dialog-verbs.ps1                 # the BORGES twin, -Phase/-DryRun/-Root
```

Exit `0` = every check passed · `1` = at least one FAIL · `2` = a fixture
precondition could not be met, **which is not a spec failure** and says so.
A `--dry-run` sends nothing and therefore never says "passed" — it reports how
many expectations it printed and asserted none of (commit `61e3fc1`).

Phases: `1` quest log · `2` quest accept · `3` trade · `4` letters + dialogs ·
`5` comms · `6` standing invariants.

## The 2026-08-31 live run: 79 PASS / 7 FAIL, and all seven were DRIVER defects

Phase 3 was run live against `_RimWorld-Agent` with zero red errors.
`3.2d`, `3.5a`, `3.5b`, `3.5c`, `3.5d`, `3.9g` and `3.9h` failed. Every one of
them was a defect in *this file*, not in `TradeVerbs.cs`. Two real mod defects
were exposed alongside them and are filed separately as git-bug `be75bc4`
(a duplicate line in one `trade-set` call) and `7e8c969` (the silent clamp is
not echoed; `AddDealTotals` is currency-inclusive). **Neither is fixed here.**

### Fix 1 — the fixture picked the SAME def for both sides of the deal
*(`3.9h`, and half of `3.9g`)*

The driver took `buyable[0]` and `sellable[0]` independently and both came back
`ComponentIndustrial`. `RimWorld/Transferable.CountToTransfer` is **one signed
field per row** and `RimWorld/Tradeable.ActionToDo` derives the side from its
sign, so a def that is bought *and* sold is a **single row**: the two writes
collapsed to `-5` and the last one won. Colony components went 50 → 45; the buy
never happened. `data.after` is keyed by `ThingDef` (`TradeVerbs.TradeConfirm`
matches `t2.ThingDef == def`), so `after_buy` and `after_sell` were **the same
object** — which is why `3.9h` failed and `3.9i` passed off one row.

The decisive tell was `lines_with_action == 2`, and that 2 was **the components
row plus the silver row**, not two item rows.

* 3.4 now searches for a `(buy, sell)` pair with **distinct defNames**,
  preferring defNames that appear on exactly one row (3.8 re-addresses by
  defName after the `Reset`, and `data.after` is keyed by `ThingDef`, so a def
  carried by two rows is ambiguous to both). No distinct pair → `note()` and
  **exit 2**, never a FAIL: that is a fixture gap.
* `3.6h` now demands `lines_with_action == 3` — two item rows *plus* silver — so
  a future collapse cannot hide behind a count that happens to match.
* `3.7c` follows for the same reason: `TradeVerbs.TradeCancel` walks
  `deal.AllTradeables` and keeps every row whose `ActionToDo` is not `None`,
  currency included, so `abandoned` is 3.
* `3.9h`/`3.9i` no longer sit behind bare `if after_buy:` guards. A missing row
  is now a FAIL; it used to make the check vanish from the run with no PASS, no
  FAIL and no mention in the RESULT line.

### Fix 2 — the silver expectation was structurally always zero *(`3.9g`)*

The driver computed `expect = sell_value - buy_value`. `TradeVerbs.AddDealTotals`
sums `CurTotalCurrencyCostForSource`/`ForDestination` over **every** tradeable
with an action, **including the silver row**, whereas
`RimWorld/TradeDeal.UpdateCurrencyCount` sums only rows where
`!tradeable.IsCurrency` and then `ForceToSource`s the silver row to absorb
exactly that difference. The currency row therefore makes the two totals equal
**by construction**: the expectation is `0` for any deal that balances, and it
would have looked right forever. The run printed `sell(98.9) - buy(99) = 0`
against a real delta of `99`.

`3.9g` now asserts the colony silver delta against
`totals.colony_silver_post_deal − totals.colony_silver`, both read
**pre-confirm** and both already published.
`RimWorld/Tradeable.CountPostDealFor(Transactor.Colony)` is
`CountHeldBy(colony) + CountToTransferToSource`, read off the currency row after
`trade-set`'s own `UpdateCurrencyCount()` — the same function
`TradeDeal.TryExecute` re-runs before resolving — so the identity is **exact
integer arithmetic**, not a tolerance. The one thing that can bend it is
`TryExecute`'s `LimitCurrencyCountToFunds()`, which caps the currency row at
`CountHeldBy(Transactor.Trader)`; that is the branch `3.8g` takes, so the driver
remembers it fired and clamps the expectation the same way.

The snapshot is taken by a `snap()` helper rather than inline, because 3.8f's
cannot-afford retry re-stages the deal — a snapshot taken only at 3.8a would be
stale by the time 3.9g read it.

### Fix 3 — the out-of-range gate was unreachable from a zero row *(`3.5a`–`3.5d`)*

The driver sent a genuinely out-of-range count (`trader_has + 9999` = 10030
against a maximum of 31) and the verb accepted it. That is **correct game
behaviour**, not a missing gate. `RimWorld/Transferable.CanAdjustTo` returns
`WasAccepted` whenever `ClampAmount(destination) != CountToTransfer`, and only
falls through to `OverflowReport()` when the clamp **equals** the current count.
From a row sitting at `CountToTransfer == 0`, `ClampAmount(10030)` is 31, 31 ≠ 0,
so the game accepts and `AdjustTo` silently writes 31. `TradeVerbs.TradeSet`'s
gate 4 calls exactly that predicate, so the gate is right and was simply never
entered — which is also why `3.5e` (no red error) passed: there was no red error
to catch.

**The gate does fire on a second identical call**, because by then
`ClampAmount(dest) == CountToTransfer`. 3.5 now sends the line **twice** and
asserts both halves: call one accepted-with-a-clamp, call two refused with
`rejected.0.gate == "out-of-range"` and the bounds echoed.

`3.5d` (`journal_seq` null on a refusal) needed no separate work. `TradeSet`
already does `seq = accepted.Count > 0 ? Act(…) : 0` and stamps the row
`accepted.Count > 0 ? Stamp(seq) : PawnActs.NoStamp()`, so seq 34 was
**correct** — the line had been accepted. It comes good as soon as the first
call is described honestly.

Call one is asserted **against what ships today**: the accepted line is
`TradeVerbs.TradeableLine` plus `was`, so it carries `count` (the clamped
result) and `was` (the count before) and carries no `requested`/`clamped`. The
clamp is therefore inferred from `count == max`. git-bug **`7e8c969`** proposes
adding the explicit echo; when it lands, `3.5d`/`3.5e` should read it directly.
Do not write that assertion before the issue ships — a check that fails until an
unrelated issue lands is a check nobody can act on.

**Check-id map for 3.5** (this is the only block whose ids moved; the `.ps1`
twin still uses the left column):

|---|---|---|
| — | `3.5a`, `3.5b` | shape: `accepted.0.was`, `accepted.0.max` are present |
| `3.5a` | `3.5c` | the **first** out-of-range line is **accepted** |

### Fix 4 — `3.2d` asserted nothing *(`3.2d`)*

`trade-start` never publishes `force_pause`. The only publishers in the mod are
`InteractionVerbs.Interactions` and `DialogVerbs`; `TradeVerbs.TradeStart` /
`PawnActs.TradeStart` is not among them. The key was **absent, not
present-null**, and `dig()` (`return default if cur is None else cur`) conflates
the two — so `eq(..., 0)` was reading a hole and the check asserted nothing. It
reported `actual: null` against `expected: 0`, which reads like a mod defect and
was not one.

**Retargeted rather than deleted.** Deleting was defensible — `3.3`'s
`stack_clear` already proves the same "no window was raised" invariant through
`status.forcePause` and it passed — but two independent routes to that invariant
is the point of a spec that is *about* the window stack, and `interactions`
publishes the richer of the two surfaces. `3.2d` now sends `interactions` right
after `trade-start` and asserts `data.force_pause.count == 0`, a path phase 0
already shape-proves at `0.5a`/`0.5b`.

Asserting `absent(e, "data.force_pause")` on the `trade-start` envelope was the
third option and was rejected: it would be a negative assertion about another
verb's payload, and it would break the day someone reasonably adds the block —
the same trap as writing `7e8c969`'s wish into `3.5` today.

## The shape contract, and the one hole that is declared rather than closed

`dig()` returns its default for an absent key and for a present-and-null one
alike, so `eq(..., None)` passes either way. A driver whose dig paths are wrong
therefore does not fail — **it goes green while asserting nothing**, which is
strictly worse than a loud abort, because nobody investigates a pass. `3.2d`
spent a whole round in exactly that state. `has_key()` is the predicate `dig()`
cannot be, and phase 0 uses it to prove every envelope key the later phases dig.

The trade totals are the one thing phase 0 **cannot** prove, and the driver says
so out loud rather than skipping it. `TradeVerbs.AddDealTotals` writes the whole
`totals` block off `TradeSession.deal`, so it exists only inside an open session
— and phase 0 has no trader to open one. So:

* `0.11` proves the **absence** half, on `0.8`'s own no-session refusal, and
  names where the other half lives.
* `3.2i`–`3.2k` prove the **presence** half on the `trade-start` envelope.
* `3.8a1`–`3.8a3` prove it again on the `trade-set` envelope `3.9g` is built
  from.

A shape contract with an undeclared hole in it is the exact failure the section
exists to prevent.

## Known remaining latent skips

`3.7j` and `3.7k` (cancel left trader/colony stock untouched) still sit behind
bare `if buy_row:` / `if sell_row:` guards, so an absent row makes them vanish
from the run rather than fail. With the buy and sell defs now distinct both rows
should always be present; the guards were left alone to keep this change
reviewable, and they are recorded here so the next round does not have to
rediscover them.
