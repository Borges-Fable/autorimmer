# Acceptance — spec 3.4, Pawn orders + policies (git-bug `39c9db7`)

The worker that wrote 3.4 may never launch RimWorld, so this is the acceptance in
executable form. `accept/3.4-pawn-orders.ps1` runs every step below and prints
`PASS`/`FAIL` per numbered check; this file is the same sequence written out, so
it can be driven by hand, by `rwa`, or by any other client.

**Every `advance` below needs the two per-call escapes** (git-bug `722c951`).
`advance` now refuses with `error.code:"unread-journal"` when the previous
advance journaled events no `journal` call has read, and halts with
`reason:"casualty"` on an own-faction downing or death. Both are right for a
play loop and wrong for a scripted fixture, which advances to move state and
never reads the journal in between — so add to every advance envelope below:

```json
"unread_ok": "<this file>: fixture, not a play loop",
"through_casualties": "<this file>: fixture, not a play loop"
```

or `--unread_ok:str '<why>' --through_casualties:str '<why>'` on the `rwa`
line. The reason is REQUIRED and non-empty, and the mod journals it as an act.
The `.py`/`.ps1` twin of this file does it in one `advance()` wrapper; by hand
it has to go on each call. Nothing else about the steps changes.

```
python3 accept/3.4-pawn-orders.py               # everything: ~90 envelopes + one `pawn` read per colonist, 147 checks
python3 accept/3.4-pawn-orders.py --phase 3     # one phase (phase 0 always runs first)
python3 accept/3.4-pawn-orders.py --dry-run     # print the plan and every expectation, send nothing
python3 accept/3.4-pawn-orders.py --root <path> # a protocol root elsewhere
pwsh accept\3.4-pawn-orders.ps1                 # the BORGES twin, same flags as -Phase/-DryRun/-Root
```

Exit `0` = every check passed · `1` = at least one FAIL · `2` = a fixture
precondition could not be met, **which is not a spec failure** and says so.
A `--dry-run` sends nothing and therefore never says "passed" — it reports how
many expectations it printed and asserted none of (commit `61e3fc1`).

> **THE `.ps1` TWIN IS BEHIND AS OF 2026-08-31, in phase 0 and phase 3 only.**
> The python driver gained phase 0's shape contract (0.6), phase 3's staged
> wardrobe (3.0), the strict 3.6c, 3.8c and the `is_null` form of 5.7b; the
> PowerShell one has none of them and still carries the version of phase 3

## Why PowerShell and the raw file protocol, not `rwa`

**BORGES has no python** — only the Microsoft Store alias stub. RUNLOG session 5
already records it ("the Windows layout line stays unexercised until python
lands"), and `rwa` is python3. An acceptance script that cannot run on the box
that has the bench is worse than none, so this driver writes
`commands/<id>.json` and reads `results/<id>.json` directly. It is the same
protocol `rwa` speaks; on a box with python, every envelope below is
`rwa <op> --args-json '<json>'`.

Ids are kept to `[A-Za-z0-9-]` so `Poller.Sanitize` leaves them alone and the
result file is exactly `<id>.json`.

> **THE ACTOR IS SELECTED, NOT INDEXED — and that is now two separate fixes.**
> The original text of this box said `pawns {filter:"colonist"}` does not
> promise a stable order (it returned a different order for the same colony
> across two calls in one session, 2026-08-31) and told you to make **every**
> colonist suitable, because "make the first colonist suitable" was not a thing
> you could arrange. Both halves have been dealt with, and they were different
> problems wearing one costume:
>
> * **The order is now promised** (git-bug 1eb2262). `pawns` emits by
>   `thingIDNumber` ascending and publishes `order:"id-asc"` beside
>   `selected_by:"attention-desc"`; phase 0 asserts both (0.3c, 0.3d) and
>   NOTEs (0.3e) if the ids come back unsorted, which means an assembly older
>   than that fix is loaded.
> * **The actor is no longer an index.** Phase 0 now reads
>   `pawn {sections:["work"]}` for every colonist and takes the first whose
>   `work.disabled` contains neither `Hauling` nor `Doctor` (0.3f); **B** is
>   simply the first colonist that is not **A** (0.3g), which satisfies 4.9's
>   "a doctor who is not the patient" by construction. Colonists that did not
>   qualify are printed with the reason (0.3h).
>
> A stable order makes an index *reproducible*; it does not make it
> *meaningful*. The over-constrained fixture — "make every colonist suitable"
> — is no longer required, and a fixture with one specialist now works.

Everything else the script stages itself with `dev:*` verbs only — 3.1's layer,
per the dispatch. **No fixture verbs and no fixture steps were added by 3.4.**

## Phase 3 — bullet 3: **a "cold" outfit policy assigned; the pawn re-dresses under advance**

### The start state is STAGED, not inherited — and until 2026-08-31 it wasn't

This phase ran live that night: **147 PASS / 3 FAIL, zero red errors.** All
three failures were one fact. The bench colonist already wore exactly
`Apparel_Parka` + `Apparel_Tuque`, which is exactly what the `cold` policy
allows. Nothing was disallowed, so `RemoveApparel` had nothing to remove
(3.6c); nothing changed, so insulation could not rise (3.6b); and 3.2's "the
pawn is not already wearing the parka" was plainly false.

**The fourth check is the one this rewrite exists for.** `3.6a` — "the pawn is
WEARING the parka" — **PASSED, and asserted nothing**: it was already true
before `policy-new` was ever sent. A green that was true before the act under
test is not evidence of the act. Repairing the three reds and leaving that
green would have left the phase exactly as blind as it was.

So the driver no longer takes its start state from whatever the save holds. It
**drives the pawn out of the warm apparel first**, proves it is out at a
precondition, and only then makes the claim. Two policies, two advances, one
bullet.

The four defs, from Core's own XML (`Data/Core/Defs/ThingDefs_Misc/Apparel_Various.xml`,
`…/Apparel_Headgear.xml`, `…/ThingDefs_Items/Items_Resource_Stuff.xml`):

| def | layer | body-part groups | `StuffEffectMultiplierInsulation_Cold` | in cloth (`StuffPower_Insulation_Cold` 18) |
|---|---|---|---|---|
| `Apparel_Pants` | OnSkin | Legs | 0.20 | 3.6 |
| `Apparel_BasicShirt` | OnSkin | Torso, Shoulders | 0.22 | 4.0 |
| `Apparel_Parka` | Shell | Torso, Neck, Shoulders, Arms | 2.00 | 36.0 |
| `Apparel_Tuque` | OnHead | (head) | 0.50 | 9.0 |

Staged pair **7.6** → warm pair **45.0**. That 45.0 is *exactly* the
`insulation_cold_total` the live run read off the unstaged colonist, which is
the arithmetic checking out against an observation rather than against a
guess; the 37-point gap means 3.6b is not a rounding argument.

**No layer collides.** `PLAIN` is OnSkin, `WARM` is Shell + OnHead, so
`ApparelUtility.CanWearTogether` would permit all four at once. The pawn ends
in the warm pair *only* because the `cold` filter stripped the plain pair —
never because it ran out of body parts, which is what makes 3.6c a statement
about `RemoveApparel` rather than about wardrobe geometry.

**One advance covers the whole cascade.** `JobGiver_OptimizeApparel` calls
`SetNextOptimizeTick` only on the paths that return `null`, never after
issuing a job, so the pawn keeps re-optimizing at each free think tick until
it settles: two removes and two wears inside one window, not one garment per
6000 ticks.

**Why 3.0j is a precondition (exit 2) and not a FAIL.** The driver's own
contract says an unmet fixture is exit 2, and three cascading FAILs for one
unstaged wardrobe is the exact defect this rewrite repairs. But **exit 2 can
understate it, and the failure text says so out loud**: the honest exit-2 cases
are a pawn that never got a free think tick (asleep, drafted, downed, mental
state, unreachable storage) or plain apparel that did not land inside a
stockpile. If B was FREE and UNFORCED and still did not undress, then
`RemoveApparel` did not run and bullet 3 is broken — a spec failure wearing a
fixture's exit code. The message prints B's worn set, its `forced_count` and
the window it waited, and tells the reader to re-run with `--echo` and read
B's job before filing it as a fixture gap.

**Why the undress leg is not circular.** It uses the same loop the bullet
tests, in the opposite direction, which does mean a broken loop cannot stage
itself. That is unavoidable: nothing in the 118-verb surface strips a pawn
without the loop. `drop` is `FloatMenuOptionProvider_DropEquipment` — the
**primary weapon only**, never apparel. `wear` is an *order*, and
`Pawn_JobTracker.TryTakeOrderedJob` sets `job.playerForced`, so
`JobDriver_Wear`'s last toil calls `forcedHandler.SetForced` — the garment is
then skipped by the very `RemoveApparel` pass under test until the pawn takes
it off, which the verb's own result note says in as many words.
`dev:destroy` resolves its target
through `Dev.ThingById`, which walks `map.listerThings.AllThings`; worn
apparel is held in the pawn's `ThingOwner` and is not in that list, so it
cannot be reached. There is no `dev:strip`. Given that, the choice is between
a staged start state whose staging shares a mechanism, and no staged start
state at all — and the second is what produced the 2026-08-31 result.

### The spec's implied mechanism is wrong, and this is the honest version

The spec bullet reads as "make it cold → the pawn dresses warm". **Weather cannot
drive this loop.** `JobGiver_OptimizeApparel` computes `neededWarmth` from
`PawnApparelGenerator.CalculateNeededWarmth`, which is
`GenTemperature.AverageTemperatureAtTileForTwelfth(tile, twelfth)` — the tile's
**seasonal average**, not the live weather. `dev:weather` moves rain, wind and
accuracy; it does not move `neededWarmth` by one degree.

What DOES drive the loop, deterministically, is the **policy filter** — which is
what the bullet is really testing ("verifies the whole clothes loop end to end"):

1. `Notify_OutfitChanged` (fired by the apparel setter) sets
   `nextApparelOptimizeTick = now`, so the pawn re-optimizes at its next free
   think tick instead of in 6000–9000.
2. The first loop in `JobGiver_OptimizeApparel` issues `RemoveApparel` for every
   worn item the new filter disallows — unconditional, no score maths.
3. `ApparelScoreGain` then multiplies a non-conflicting candidate's score by
   **10**, so a parka on a now-bare torso is a large positive gain, well over the
   `MinScoreGainToCare` floor of 0.05.

So the fixture is "a policy that allows only warm apparel, with that apparel in
storage", and the mechanism is filter-driven and season-independent. Flagged on
the issue.

**That reasoning was right and is unchanged. What it was missing** is that
"a policy that allows only warm apparel" is only half a fixture — the other
half is *a pawn that is not already wearing it*, and the bench cannot promise
that. Step 3.0 supplies it, by running exactly the mechanism above in reverse:
a policy that allows only the plain pair, which makes the parka and tuque the
disallowed items step 2 removes. Same three numbered steps, opposite
direction.

**Why the fallback window.** `nextApparelOptimizeTick = now` makes the pawn
eligible immediately, but it still has to be free: asleep, eating, in a mental
state or mid-job all delay the think pass. 5000 ticks covers the ordinary case;
20000 covers a sleeping pawn. Both of phase 3's advances use that pair, and
both are preceded by `dev:set-need {need:"Rest"|"Food",val:1.0}` on B, which
is the fixture row that used to be handed to a human. Note that the window now
has more to cover: the cold leg is two `RemoveApparel`s (each with a haul) and
two `Wear`s rather than one job, so the fallback firing is ordinary rather
than a warning sign — and it is a NOTE, not a check.

## What this script does NOT prove

- **The python driver has been run once, live, on 2026-08-31** — 147 PASS /
  3 FAIL, zero red errors — and phase 3 was rewritten out of what that run
  showed. Everything else is still derived from the decompiled 1.6 source and
  the shipped serializers' field names rather than from an observed run, and
  the `.ps1` twin has never been run at all. **Phase 3's rewrite itself is
  unrun:** it is derived from `JobGiver_OptimizeApparel.TryGiveJob`,
  `JobDriver_RemoveApparel.MakeNewToils`, `JobDriver_Wear.Notify_Starting`,
  Core's apparel XML and `Humanlike.xml`'s think-tree ordering (which puts
  `JobGiver_OptimizeApparel` **above** `MainColonistBehaviorCore`, so the
  re-dress beats work, joy and the timetable's sleep block).
- **A dry run proves nothing.** It sends no envelope and evaluates no
  expectation, and the runner says exactly that instead of "passed"
  (commit `61e3fc1`). Use it to read the plan, never as a green.
- **It is not a coverage sweep.** 35 verbs ship; this exercises about 25 of them.
  `attack`, `rescue`, `capture`, `carry`, `equip`, `drop`, `consume`,
  `extinguish`, `beat-fire`, `repair`, `man-turret`, `policy-edit` and
  `policy-default` have no step here — each needs a fixture (a hostile in melee
  range, a downed pawn, a live fire, a damaged building, a turret) that is more
  staging than the four acceptance bullets ask for. Their gates are cited in code
  and their reject paths are the same shape as the ones phase 5 does exercise.
- **Timing windows are estimates, not measurements.** Where a window is chosen,
  the reasoning is written above it and a fallback window is attempted before the
  check fails, so "too slow" is distinguishable from "never happened".
- **`prioritizeSustains` for `HaulGeneral` is asserted as a bool, not as `true`.**
  Core does not set it on that work giver, so phase 2 verifies only the result's
  honesty about *not* writing (`sustains:false` + "no standing order was
  written"). The write itself is exercised at 5.17 with
  `DoctorTendToHumanlikes`, which does set it — in Core the sustaining set is the
  doctor, bill-worker and construction givers (`DoBills*`, `ConstructFinishFrames`,
  `Construct/DeliverResourcesTo*`, `FixBrokenDownBuilding`, `Refuel`,
  `RearmTurrets`, `Train`, `TakeToPen`), **not** mining or sowing, which is worth
  knowing before writing another test against a guess.
