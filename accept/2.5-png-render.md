## Known risks, from the worker, before anyone runs this

- **`--whole-map` is the riskiest call here and was never measured.**
  `map-dump` reads `Room.Role` once per distinct room — cheap for a
  base-sized rect, but a whole map is every room on the map, each potentially
  triggering `UpdateRoomStatsAndRole()`, the lazy full room analysis
  `DigestVerb`'s header warns about. Idempotent and RNG-free, so nothing is
  corrupted, but it runs on the main thread at the safe point. If it hitches or
  trips the stall watchdog, `--layers terrain,things,zones,roof` drops the rooms
  plane and the cost with it. **Treat whole-map as optional and last.**
- **`ROOM_TINTS` has 12 entries and cycles.** A base with more than 12 enclosed
  rooms reuses colours, and since the per-room boundary stroke is drawn in each
  room's own tint, two adjacent rooms 12 apart in palette order share both. **If
  room-counting is the question that fails, this is the cause**, and the fix is a
  longer tint list, not a redesign.
- Legibility was verified by the worker on the synthetic fixture — by reading
  the PNG back as an image, which is how four defects were found and fixed (the
  legend running off the right edge, fog reading as empty space rather than
  unexplored ground, zone corner-ticks that looked like pawns, glyphs smudged
  inside a 12px swatch). But that fixture is two tidy rectangular rooms with
  five defs. A real base is neither.

## The one design fact that makes this cheap: NO ROOF IS NEEDED

`Verse/Room.cs` `PsychologicallyOutdoors` is true only when
`OpenRoofCountStopAt(300) >= 300`, or when `TouchesMapEdge` **and** at least
half the cells are unroofed. `ProperRoom` is `!TouchesMapEdge` plus one
district of `RegionType.Normal`. So a walled enclosure of well under 300 cells,
sited away from the map edge, is a **proper, psychologically-indoor room with
no roof at all** — which matters because nothing in the verb surface can place
a roof (`grep -n roof Source/AutoRimmer/*.cs`: only `area build-roof add`,
which merely designates and waits for a colonist). CONFIRMED AT SOURCE.

`Verse/Room.cs` `UpdateRoomStatsAndRole` computes a role only when
`ProperRoom && RegionCount <= 60`, else `RoomRoleDefOf.None`. With a role
computed, `RimWorld/RoomRoleWorker_Kitchen.GetScore` scores 28 per
Production-category building whose recipes yield human-edible nutrition, and
`RoomRoleWorker_Room.GetScore` returns 0.99 — so **the stove room's role is
`kitchen` and the empty room's is `room`**, and `baseviz/render.py`
`_room_name_pass` writes those words inside the rooms. CONFIRMED AT SOURCE.

## Chaining: why this fixture cannot hit `0d9cbd7`, and where it still could

`0d9cbd7`'s mechanism is a later step **re-resolving its target by first-match
over a live lister** (`WorldFixtureVerbs.FindBench` walking
`ThingsInGroup(PotentialBillGiver)`). Nothing in this sequence does that:

- `dev:spawn-thing` never searches. It takes `pos`, and
  `Positions.Resolve(map, "x,z")` is pure integer parsing
  (`Source/AutoRimmer/Spatial.cs` `Positions.ResolveString`). **Every build
  step is absolute-coordinate addressed**, so there is no handle to lose.
- The only value read back and re-used is `find-rect`'s
  `data.candidates[0].at`, read ONCE into shell variables `X0`/`Z0` and never
  re-derived. That collapses 38 potential chains into one.
- The verification steps chain by **explicit id**, and both routes are exact
  lookups, not first-match scans:
  - `room-at {at:[x,z]}` publishes the room in **`data.id`**
    (`Source/AutoRimmer/SpatialVerbs.cs` `RoomAt`).
  - `room {id:<that>}` resolves through `WorldSafe.FindRoom`, which compares
    `all[i].ID == id`. Exact.
  - `things {def:…, in:"room:<that>"}` resolves through the same
    `WorldSafe.FindRoom` (`ThingVerbs.Scope.Resolve`). Exact.
  - `dev:spawn-thing` publishes each thing's id in **`data.spawned[0].id`**
    (`Dev.Describe`) — that is the field to quote if you ever need to address
    one specific wall.

**Risks I could NOT eliminate, in descending order:**

1. **`dev:spawn-thing` reports a refused placement as `ok:true`.** When
   `GenSpawn.CanSpawnAt` says no, `SpawnThing` `break`s the loop and still
   returns a normal success envelope carrying `placed:0` and a `failed[]`
   block. `rwa`'s exit code is 0. A `set -e` script that does not read
   `data.placed` will build a wall with a hole in it and never notice. The
   script below checks `placed == 1` on every single call; **do not drop that
   check.**
2. **A stale DLL is invisible until the render is wrong.** `doorway`/`proper`
   in the rooms palette and `impassable`/`natural_rock` in the things palette
   arrive from `848a791`. `baseviz/render.py` `proper_rooms` falls back
   silently when `proper` is absent — so an old assembly yields "3 enclosed
   rooms" (two rooms plus the door pocket) and looks like a legibility failure.
   The script asserts those keys are present in the dump.
3. **The colony moves between calls.** Mitigated by `pause` first: verbs run on
   `GameComponentUpdate` (`AgentGameComponent.cs`), which ticks while paused,
   and `IntVec3.GetRoom` forces `TryRebuildDirtyRegionsAndRooms` on its own
   (`Verse/RegionGrid.GetValidRegionAt`), so rooms are correct while paused. If
   you unpause afterwards, colonists will roof the rooms
   (`Verse/AutoBuildRoofAreaSetter`) and any PNG taken before that no longer
   matches the map.
4. **`rooms` reads `map.regionGrid.AllRooms`, which does NOT rebuild.** Only
   `GetValidRegionAt` / `DirectGrid` / `AllRegions` do. The script therefore
   calls `room-at` (which does rebuild) before `rooms`. Keep that order.
5. **Codes are not stable tokens.** `baseviz/render.py` `assign_codes` walks
   the second character through `_ALT` on collision, so `ES` is the *expected*
   code but the legend, not this document, is the authority. Grade on "the code
   the legend maps to ELECTRIC STOVE", never on the literal `ES`.
6. **FIXED as of rwa 0.2.0 — `rwa room --id N` now works.** This trap
   previously read: *"`rwa room --id N` DOES NOT WORK. `--id` is a global `rwa`
   flag — the command id — listed in `GLOBALS`, and `parse_globals` pulls it out
   of argv wherever it appears, before the op ever sees it. So `rwa room --id
   501` sends `room {}` with the command id `501`, and the bench answers
   `bad-args: missing required arg 'id' (number)`, which reads as if the verb
   were broken."* That was true, it cost the M1 run real time mid-emergency, and
   it is now repaired: **rwa's own command id is `--cmd-id`**, and a bare `--id`
   is an ordinary op argument that reaches the verb. `id` was the only VerbArgs
   key in all of `Source/AutoRimmer/` colliding with `GLOBALS`, so the reserved
   table is now disjoint from the verb namespace — keep it that way when adding
   a global.
   The `--args-json "{\"id\":$id}"` form used below still works and is left in
   place; it is no longer the only form that does. The trap is kept rather than
   deleted because of what it taught: **a wrong argument name here is silent**,
   the same class as the `things`-has-no-`filter` trap, and it was found by
   dry-running the script against a stub client rather than on a bench.

## devMode

Every `dev:*` verb opens with `Dev.Gate(V)` (`Source/AutoRimmer/DevVerbs.cs`,
`Dev.Gate`), which throws `VerbArgsException` when `Prefs.DevMode` is false.
That becomes `ok:false, code:bad-args, detail:"dev:spawn-thing requires
devMode=True (the dev layer mutates game state by design)"`, and `rwa` returns
a non-zero exit (`env_exit`). With `set -e` the script **stops on the one-cell
`dev:unfog` probe in step 1**, before a single wall is placed. The bench
profile seeds `devMode=True` (spike 0.1); if it is off, turn it on and re-run
from the top — nothing will have been half-built.

  devMode off aborts on the `dev:unfog` probe with **0 spawns made**; an

## The grading key

Fill from the script's `=== GRADING KEY ===` block; predicted values are for a
clean run at `W=11 H=7 R=12` on `autostart.rws`.

| # | correct answer | predicted | grade |
|---|---|---|---|
| 1 | `ENCLOSED ROOMS` from the key | **2** | exact number or FAIL. "2 rooms plus a doorway" is a PASS; "3" is the door-pocket failure |
| 2 | every `DOORS` coordinate from the key | **1**, at `(DX,DZ)` — plus any pre-existing colony door inside the rect, which the key lists | every door found, coordinates within ±1 cell |
| 3 | the room named `KITCHEN` — the **west** room, id from the key | west room | PASS if named by position ("the left/west room") or by its printed name |
| 4 | the stove occupies `X0+1 .. X0+3` at `z=DZ`; published centre `(X0+2, DZ)` | — | ±1 cell in x, exact in z |

Notes for the grader:

- **A reader is spent after one image.** A second iteration needs a second
  fresh session; do not re-ask the same one.
- Q1's failure mode to watch for is the reader counting the *doorway* as a
  third room. That is precisely the `848a791` defect, so if it happens check
  `palettes.rooms` for `doorway`/`proper` before blaming the reader. The script
  asserts this; a hand-run render will not.
- Q4's ±1 tolerance in x is deliberate: `_label_pass` centres the code at
  `at + size/2` while `map-dump` publishes `at = Thing.Position`, which for an
  **odd** width ≥3 is the middle cell, not the min corner
  (`Verse/GenAdj.OccupiedRect`). The 3x1 stove's code therefore renders one
  cell east of true centre. Cosmetic — it still lands on the stove — and it is
  **not fixed here**, because this worker's writable territory is this file
  alone. Worth its own issue.
- The legend is allowed. "Legible" means legible with the key the image itself
  carries; `_legend_rows` prints `ENCLOSED ROOMS: N (DOORWAYS AND OUTDOORS
  EXCLUDED)` as its own row, so a reader answering Q1 straight off the legend
  has passed the question the spec asked.

## `--landmarks`: it CAN be registered, and here is the check that proves it

The registry is written by the ordinary `landmark` verb —
`Source/AutoRimmer/SpatialVerbs.cs` `Landmark`, `{set:{name, at}}` — which is
**not** `dev:*` and needs no devMode. `LandmarkComponent.Set` stores it and
`ExposeData` persists it. `rwa render --landmarks` sends `landmark {}` and
reads `data.landmarks` (`rwa/rwa` `cmd_render`, section 3); `baseviz/render.py`
step 8 strokes a box at each landmark inside the rect and, at `scale >= 8`,
writes its name beside it. CONFIRMED AT SOURCE.

The previous run's "identical hash with and without `--landmarks`" was the
signature of an empty registry, i.e. an untested code path, not a passing one.
Section 6 above inverts the assertion: with two landmarks registered inside the
rect the two renders **must differ**, and the script fails if they do not.

Names are deliberately `fixture-nw` / `fixture-se`, on wall corners. A landmark
called `stove` or `door` would be drawn on the image in capitals and would hand
the reader the answers — which is also why the landmark render is produced
**after** the graded ones and must never be the file handed to a reader.

`--landmarks` is bench-only: `cmd_render` warns and ignores it on the offline
`--dump` path. That is by design, not a gap.
